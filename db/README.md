# 부여GP 일보 시스템 — PostgreSQL 스키마

설계문서 `../design/부여GP_일보시스템_설계문서_v2.md` (v2.4) 의 4장 데이터 모델,
5장 오류 방지·검출 체계, 6장 권한 설계를 실행 가능한 DDL 로 확정한 것이다.

- 요구 버전: **PostgreSQL 15 이상** (`UNIQUE NULLS NOT DISTINCT` 사용)
- 실행: `psql -v ON_ERROR_STOP=1 -f 000_run_all.sql`  ·  대상: Supabase(서울) 또는 로컬 PG
- 테이블 57개 · 뷰 16개 · 함수 38개 · 트리거 57개 · RLS 정책 66개
- 마스터 시드: 돈방 133 · 집계행 25 · 약품 153 · 사료 12 — **전부 엑셀 판독본**
- 정적 점검: `python tools/check_sql.py`

> **검증 상태**: **Supabase(서울) PostgreSQL 17.6 에 적용 완료.**
> 17개 파일 1.3초, 동작 시험 43건 전원 통과, 과거 자료 3,681행 적재 완료.
> 정적 검사는 `tools/check_sql.py`, 동작 검증은 `api/src/db/verify.js` 가 맡는다.

```bash
cd api
npm run migrate          # 스키마 적용
npm run verify           # 동작 검증 43건
npm run load:m3          # 과거 자료 적재
npm run setup:role       # 앱 계정 생성 + RLS 실제 적용 확인
```

## 일보 판독 결과 — 설계문서에 없던 구조

`자료들/` 의 일보 엑셀 5종을 직접 파싱했다(`tools/gen_016_seed_pen.py`).
그 과정에서 **설계문서 §4.11 의 `pen_daily(report, pen, batch)` 모델로는
표현할 수 없는 구조**가 확인되어 스키마를 고쳤다.

### 돈사마다 두수 행을 쪼개는 축이 다르다

| 돈사 | 일보의 행 구성 | `house.count_basis` |
|---|---|---|
| 순치사 · 종부사 · 임신1동 · 임신2동 | **돈방 없음.** 돈사 × 축종구분 | `category` |
| 분만1동 · 분만2동 | 돈방 × 축종구분 4열(분만대기돈·포유모돈·포유자돈·이유자돈) | `pen_category` |
| 자돈사 · 육성사 · 검정사 · 비육사(수) | 돈방 × 돈군 | `pen` |
| 계류장 | 돈사 1행 | `house` |

종부사일보는 28개 블록 전부가 아래 17행으로 동일했다.

```
순치사   후보(수) · 후보(암) · 이유모돈 · 체류돈 · 임신돈
종부사   웅돈 · 후보(암) · 이유돈 · 단기체류 · 장기체류 · 임신돈
임신1동  후보(암) · 단기체류 · 임신돈
임신2동  후보(암) · 단기체류 · 임신돈
```

**대응** — `pen_daily.pen_id` 를 nullable 로 바꾸고 `house_id`·`category_id` 를 더했다.
행 식별 키는 `(report, pen, batch, category)` 이며 V2 전일두수 이월,
V7 폐사 대사, L1-COMPLETE 판정이 모두 이 키를 쓴다.
어떤 행이 있어야 하는지는 `house.count_basis` + `house_category` 로 데이터가 결정한다.

`mortality`·`culling` 도 같은 이유로 `pen_id` 를 nullable 로, `house_id` 를 필수로 바꿨다.
종부사 폐사는 돈방이 없기 때문이다.

### 실제 돈방 수는 문서의 「약 110개」 보다 많다

| 돈사 | 돈방 | 블록 수 | 목록 안정성 |
|---|---:|---:|---|
| 분만1동 | 11 | 27 | 전 블록 동일 |
| 분만2동 | 11 | 27 | 전 블록 동일 |
| 자돈사 | 28 | 28 | 전 블록 동일 |
| 육성사 | 15 | 16 | **15/16 동일** — 1개 블록에서 `2-1` 누락 |
| 검정사 | 40 | 16 | 전 블록 동일 |
| 비육사(수) | 28 | 17 | 전 블록 동일 |
| **계** | **133** | | |

- 육성사 1개 블록의 `2-1` 누락은 현행 엑셀의 **행 누락**이다. 최빈 목록(15방)을 채택했다.
- 비육사(수)에는 **2동이 없다** — 1·3·4·5·6동만 쓴다.
- `pen.active_from` 은 전건 `2026-08-06`(엑셀 일보 운영 개시일)으로 넣었다.
  그 이전은 전량 종이 작성이므로 적재 대상이 아니다(§1.1, 회신 109번).

### 축종구분 마스터를 5개 늘렸다

설계문서 §4.1 목록에 일보에서만 확인되는 항목을 더했다 — `이유돈`(종부사),
`단기체류`·`장기체류`(§11.3 종부 미실시 1주 이내/초과), `분만대기돈`·`이유자돈`(분만사 열).

## 실행 검증이 잡아낸 것

정적 검사로는 문법과 참조만 본다. **트리거가 정말 막는지, 생성열이 정말 계산하는지는
DB 에 올려서 시켜봐야 안다.** 실제로 올려보니 정적 검사가 통과시킨 결함 두 건이 나왔다.

### 1. 함수 37개 중 33개에 `search_path` 가 없었다

plpgsql 함수 안의 무자격 이름(`daily_report`)은 **함수를 부르는 세션의 search_path** 로
해석된다. 마이그레이션 파일은 맨 위에 `SET search_path` 를 두지만 그건 그 세션 한정이다.
다른 클라이언트가 붙으면 트리거가 전부 이렇게 죽는다.

```
error: relation "daily_report" does not exist
  where: PL/pgSQL function app.fn_pen_daily_before() line 8
```

운영에서 터졌을 버그다. 전 함수 정의에 `SET search_path = app, sec, extensions, public`
을 박아 고쳤다. search_path 가로채기 방어도 겸한다.

### 2. RLS 공백 6개 테이블

`farm_id` 를 들고 있는데 정책 루프 목록에서 빠져 있었다 —
`house_category` · `movement_schedule` · `feed_stock_monthly` · `medicine_stock_monthly`.
일보에 딸린 `report_comment` · `submission_signature` 도 부모를 따라가도록 추가했다.
정책이 63 → 74개가 됐다.

의도적으로 RLS 를 걸지 않는 테이블은 014 에 목록으로 적어 두었다 —
전 농장 공용 마스터와 부모에 종속된 라인 테이블이다.

### RLS 가 실제로 걸리는지도 확인했다

마이그레이션은 소유자(`postgres`)로 돌기 때문에 RLS 를 우회한다.
그래서 **「정책을 만들었다」와 「정책이 작동한다」는 별개**이고, 확인해야 안다.
`buyeogp_api` 로 직접 붙어 본 결과다.

| 시험 | 결과 |
|---|---|
| 신원(`app.user_id`) 미설정 시 일보 조회 | **0행** (소유자로는 3,681행) |
| 스코프 없는 사용자로 돈방 조회 | **0행** |
| `sec.app_user` 쓰기 | **거부** (SoD-3) |
| 감사로그 UPDATE·DELETE 권한 | **없음** |

## 과거 자료를 판독해 확인한 것 (M3)

현행 일보 엑셀 5종을 전수 판독했다(`tools/parse_daily_reports.py`).
**3,682행 · 29일(2026-08-06 ~ 09-03)** 이며 보고서는 `migration/m3_report.md` 에 있다.

### 설계문서 D3 「거의 매일 발생하는 계산 실수」는 재현되지 않았다

| 검사 | 결과 |
|---|---|
| 행 검산 (`전일 + 전입 − 전출 − 내부전출 − 판매 − 폐사 = 당일`) | 3,682건 중 **불일치 6건** (99.84%) |
| 전일두수 연속성 (어제 당일 = 오늘 전일) | 3,491쌍 중 **불일치 5건** |
| 종합일보 ↔ 개별일보 (돈사별 두수합계, 20일 × 6돈사) | **120건 전부 일치** |

이유는 판독 중에 드러났다 — **「당일두수」 칸이 100% 엑셀 수식이다.**
전일두수도 87%가 수식(전날 시트 참조)이다. 행 단위 산수는 사람이 하지 않으므로
틀릴 수가 없다.

그러면 회신 31번의 「계산 실수가 거의 매일」은 무엇인가. 확보된 자료로는 답할 수 없다.
셋 중 하나일 것이다.

1. 입력값 자체의 오류 — 두수를 잘못 세거나 잘못 친 것. 엑셀에는 흔적이 남지 않는다
2. 중간에 고쳐진 것 — 엑셀에 수정 이력이 없다(D9). 내가 본 것은 최종본뿐이다
3. 합계·월계·타시트 참조가 깨진 경우 — 이번 검사 범위 밖이다

### 다만 엑셀이 음수 두수를 계산해 둔 곳이 있었다

적재 중 V3(재고 초과 출고 금지)가 한 행을 거부했다.

```
2026-09-02  순치사 이유모돈   전일 4 · 전출 52  →  당일두수 −48
```

8/30 의 전출 52 가 9/2 에 그대로 다시 들어간 것으로 보인다. **엑셀은 −48 을 그대로
계산해 두었고 아무도 발견하지 못했다.** 돼지가 음수로 존재할 수는 없다.

이 한 건이 D3 의 성격을 보여준다. 산수가 틀린 게 아니라 — 수식은 정확히 −48 을
계산했다 — **말이 안 되는 값을 걸러낼 장치가 없다.** 신규 시스템은 저장 자체를 거부한다(P7).

거부된 행은 `app.m3_rejected` 에 사유와 함께 남는다. 원본은 `app.m3_daily_raw` 에
그대로 있으므로 잃는 정보는 없다.

**이 결과가 프로젝트의 근거를 약화시키지는 않는다.** 오히려 정확한 진단이다.
현행의 문제는 산수가 아니라 (a) 같은 사실을 세 곳에 서로 다른 구조로 적는 것(D1),
(b) 스크린샷으로 전달하는 것(D2), (c) 누가 언제 무엇을 고쳤는지 모르는 것(D9)이다.
이 셋은 수식으로 해결되지 않는다.

> **다만 범위를 분명히 해 둔다.** 종합일보 대조는 축종구분 단위 돈사 6개만 했다.
> 자돈사·육성사·검정사·비육사는 종합일보에서 돈방이 열로 눕는 전치 레이아웃이라
> 별도 파서가 필요하다. 남은 검증 항목이다.

### 두 문서가 같은 돈사를 다르게 쪼갠다 (D1 의 증거)

```
순치사   개별일보  후보(수) · 후보(암) · 이유모돈 · 체류돈 · 임신돈
         종합일보  후보(암) · 웅돈 · 도태대기 · 이유모돈 · 장기체류돈 · 임신돈
종부사   개별일보  웅돈 · 후보(암) · 이유돈 · 단기체류 · 장기체류 · 임신돈
         종합일보  후보(암) · 단기체류(이유모돈) · 장기체류 · 도태대기 · 임신돈
```

항목 단위로는 대조 자체가 불가능하고 합계로만 맞댈 수 있다.
종합일보를 뷰로 만들면(§4.13) 이 불일치가 원천적으로 사라진다.

### 원본 구조에서 새로 확인한 것

### 약품 마스터에 구멍이 있다

재고관리 파일에서 **153품목**을 뽑았다(설계문서가 본 거래명세표 20품목보다 넓다).
그런데 **휴약기간이 확인된 것은 27품목뿐이고 126품목이 미상**이다.

V9(휴약기간 미경과 출하·도태 차단)가 이 값을 그대로 쓴다. 미상을 0 으로 넣어 두면
**실제로는 휴약기간이 있는데 차단이 작동하지 않는다.** 거래명세표를 더 받거나
품목별로 확인해 채워야 한다 — 목록은 `migration/m3_feed_report.md` 에 있다.

## 설계 원칙이 스키마에 박힌 방식

설계문서의 원칙 중 **코드가 아니라 스키마가 보장하는 것**을 분리했다.
애플리케이션 버그가 있어도 아래는 깨지지 않는다.

| 원칙 | 구현 |
|---|---|
| P5 계산은 전부 시스템이 | `pen_daily.closing_head`, `farrowing.live_born`, `breeding.expected_farrow_date`, `medicine_usage.withdrawal_until`, `shipment.avg_weight_kg` 를 **생성열**로 두었다. 사람이 입력할 수 없고 틀릴 수 없다 |
| V1 돈방 검산 등식 | 위와 같음 — 등식이 열 정의 자체다. 위반이 **불가능**하다 |
| V3 재고 음수 금지 | `CHECK (출고합계 ≤ opening + in)` |
| V4 중복 금지 | `UNIQUE NULLS NOT DISTINCT (report_id, pen_id, batch_id, category_id)` — 빈 돈방도 1행만 |
| V6 분만 실산 등식 | `live_born` 생성열 + `CHECK (구성요소 합 ≤ 총산)` |
| V6-3 분만예정일 | `GENERATED ALWAYS AS (mating_date + 114)` |
| SoD-1 입력자 ≠ 확정자 | `CHECK (confirmed_by <> author_id)` |
| SoD-2 발행자 ≠ 승인자 | `CHECK (approved_by <> issued_by)` |
| SoD-3 admin 업무데이터 차단 | `app` 스키마를 `buyeogp_admin` 에 GRANT 하지 않음 |
| 감사로그 불변 | `RULE ... DO INSTEAD NOTHING` + `REVOKE UPDATE, DELETE` |
| 멀티테넌시 | 모든 업무 테이블이 `farm_id` 를 들고, `(id, farm_id)` 복합 FK 로 교차 테넌트 혼입을 차단 |

트리거로 가는 것: V2(전일두수 자동이월·수정불가), V5(전일 미확정 시 입력 차단),
V7(폐사·도태 두수를 원장에서 파생), V8(이동 1:N 상태 재계산), V9(휴약기간 출하 차단),
P4(확정 후 원본 불변).

함수로 가는 것: `fn_validate_report`(제출 게이트), `fn_detect_anomalies`(L4 14종),
`fn_day_close_gate`(L5 5조건).

| 문서 | 처리 | 이유 |
|---|---|---|
| `pen_daily.age_days`, `week_no` | `v_pen_daily` 뷰에서 계산 | `report_date` 와 `batch.birth_date_avg` 의 순함수다. 저장하면 두 값이 어긋날 수 있다 |
| 대장 하단 주차 집계 | `v_breeding_weekly` / `v_farrowing_weekly` | 문서 §4.6.1 이 이미 「시스템에서 사라진다」고 명시 |

### 4. 이름을 바꾼 것

- `user` → `sec.app_user` (SQL 예약어)
- `exception` → `exception_queue` (PL/pgSQL 키워드와 혼동)

### 5. 해석이 필요했던 것

**`movement_line` 합계가 `total_head` 와 다를 때.**
문서가 두 곳에서 다르게 말한다 — §5.4 V8 은 「저장 거부」, §5.5 는 「불일치 시 disputed」.
다음으로 해석했다.

```
합계 = 0        → pending    (수령 대기)
합계 = total    → matched
0 < 합계 < total→ disputed   (양쪽 화면 + 본사 예외 큐)
합계 > total    → 저장 거부   (발신보다 많이 받는 것은 물리적으로 불가능)
```

마감 시 `pending`/`disputed` 0건을 요구하므로(L5) 두 서술이 모두 만족된다.

**`(30kg 기준 ±2,500원)` 이 두당인지 총액인지.**
회신에 없다. `settlement_shipment.weight_adjust_amount` 에 **조정 결과 금액**을 그대로
보관하고, `actual_amount`(실제 정산서 금액)와 `diff_amount` 를 함께 두었다.
R-B 대로 첫 정산에서 대조해 산식을 확정하면 된다.

## 스키마가 담당하지 않는 것

의도적으로 애플리케이션 계층에 남긴 것이다. RLS 와 트리거에 업무 규칙을 모두
밀어 넣으면 디버깅이 불가능해진다.

- **L0 필드 검증** — 브라우저에서 즉시. DB CHECK 는 최후 방어선일 뿐이다
- **L1 실시간 검산 뱃지** — 그리드 UI. DB 는 생성열로 결과만 보장한다
- **상태 전이 권한** — 누가 확정할 수 있는가는 트리거(`fn_report_status_guard`)가
  전이 자체를, RLS 가 접근 범위를 본다. 역할별 버튼 노출은 프런트
- **정정전표 적용 로직** — `adjustment.payload`(jsonb)를 실제 테이블에 반영하는 것은
  서비스 계층. DB 는 `app.adjustment_id` 세션 변수가 설정된 동안만 확정본 수정을 허용한다
- **PDF 생성·서명** — `daily_report.printed_at`/`signed_at` 과
  `submission_signature.content_hash` 만 DB 가 보관한다
