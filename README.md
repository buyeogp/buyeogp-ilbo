# 부여GP 돈사 일보 전산화 시스템

농업회사법인 (주) 부여지피의 돈사 일보를 전산화한다.
현재 현장 팀장 4명이 엑셀에 입력하고, 화면을 캡처해 카카오톡으로 보내면
본사가 종합일보에 다시 입력한다. 같은 사실이 세 곳에 적힌다.

설계 근거는 `design/부여GP_일보시스템_설계문서_v2.md` (v2.4) 다.

```
design/     설계문서 v2.4
db/         PostgreSQL 스키마 · 마스터 시드 · 과거자료 적재
api/        백엔드 — 인증 · 권한 · 일보 · PDF
web/        화면 — 일보 입력 그리드 · 제출 현황
infra/      배포 구성 (Supabase 서울 + 앱 서버 1대 + Cloudflare)
자료들/      원천 자료 (git 제외 — 개인정보 포함, 300MB+)
```

## 주요 판단과 근거

설계문서와 달라진 부분, 그리고 판독으로 새로 확인한 사실은 각 README 에 근거와 함께
적어 두었다. 요약하면 셋이다.

**1. 돈사마다 일보의 행을 쪼개는 축이 다르다.**
설계문서는 `pen_daily(report, pen, batch)` 하나로 전 돈사를 상정했으나,
종부사·임신사는 돈방 없이 축종구분으로만 집계하고 분만사는 돈방 × 축종구분이다.
행 식별 키를 `(돈사, 돈방, 돈군, 축종구분)` 으로 넓히고 `house.count_basis` 로
어떤 행이 있어야 하는지를 데이터가 정하게 했다. → `db/README.md`

**2. 「거의 매일 발생하는 계산 실수」는 재현되지 않았다.**
일보의 당일두수 칸이 100% 엑셀 수식이라 행 단위 산수는 틀릴 수가 없다.
3,682행 중 불일치 6건, 종합일보 재입력 대조 120건 전부 일치.
현행의 실제 문제는 산수가 아니라 중복 기록·전달 매체·이력 부재다. → `db/README.md`

**3. HACCP 때문에 서버가 한 대 필요하다.**
전자기록이 인정되지 않아 시스템이 종이를 만들어야 하고(§6.5), 출력물과 데이터가
같다는 증명(`content_hash`)이 서버에서 나와야 한다. Chromium 이 도는 자리가
있어야 하므로 서버리스만으로는 구성할 수 없다. → `api/README.md`

**3. 실행해봐야 아는 결함이 있었다.**
정적 검사를 통과한 스키마를 실제로 올렸더니 두 건이 나왔다 — 함수 33개의
`search_path` 누락(운영에서 트리거가 전부 죽는다)과 RLS 공백 6개 테이블.
DB 에 올려서 시켜보기 전에는 알 수 없는 것들이었다. → `db/README.md`

## 가동 시작 시점의 결정 — 과거 일보 일괄 적재

두수는 **원장**이다. 오늘의 전일두수는 마지막으로 확정된 날의 당일두수를 잇는다.
DB 에는 `2026-09-03` 까지 들어 있으므로, 전산 개시일까지의 일보가 비어 있으면
그 기간만큼 두수가 현실과 어긋난 채로 시작한다.

**빈 기간의 엑셀 일보를 일괄 적재하기로 한다** (2026-09-21 결정).
자료가 모이면 진행한다.

개시 재고(`is_baseline` — 특정 날짜 실사 두수만 찍고 시작)를 쓰지 않는 이유는,
그러면 그 사이의 폐사·출하·이동 기록이 통째로 사라지기 때문이다. HACCP 3년 보존과
추적성(§6.5)을 생각하면 일괄 적재가 맞고, 자료가 이미 엑셀에 있어 새로 만들 것도 없다.

절차는 지난번 4주치와 같다 — `python db/tools/parse_daily_reports.py` → `npm run load:m3`
→ `npm run verify`. 규칙에 걸린 행은 `app.m3_rejected` 로 격리되므로 **넘어가지 말고
현장에 확인한다**. 지난번에는 3,682행 중 1행(엑셀에 당일두수가 −48)이 걸렸다.
