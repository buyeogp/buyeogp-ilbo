현장 회신으로 이전 설계의 주요 전제가 바뀌었다. 잘못된 방향으로 설계된 부분을 먼저 정정한다.

| # | v1.x 전제 | v2.0 확인된 사실 | 영향 |
|---|---|---|---|

## 1. 현행 분석

### 1.1 업무 흐름 (확정)

```
[돈사]                    [현장사무실]                 [서울 본사]
작업자 메모        팀장이 엑셀 직접 입력        종합일보에 재입력
(변동·특이사항만)   (돈사별 담당 팀장 1명)       → 최종 검토
       │                      │                        ▲
       └── 업무 종료 후 ──────┘                        │
                              └─ 18:30 이후 ───────────┘
                                 엑셀 화면 캡처 → 카카오톡 전송
```

- 작업자는 일보를 들고 다니지 않는다. 그날의 변동·특이사항을 메모해 두었다가 업무 후 정리한다
- 메모 원본은 돈사별 사무실에 **1년** 보관 (HACCP 요건은 3년 — 1.5 F1)
- 8월 6일부터 엑셀 운영. **그 이전은 전량 종이 작성**이었다 (분만사 8/15 결측의 원인)
- 육성사·검정사·비육사는 8월 18일부터 엑셀 운영

### 1.2 인력 구조

| 구분 | 종부사 | 분만사 | 자돈사 | 육성·비육·검정 | 계 |
|---|---:|---:|---:|---:|---:|
| 현장 작업자 | 4 | 5 | 2 | 7 | 18 |
| PC 입력 팀장 | 1 | 1 | 1 | 1 | 4 |

- 팀장 배정은 고정, 팀원은 가끔 변경
- 입력자 전원 외국인(네팔). 캄보디아 국적 1명은 일보 작성과 무관
- 이직·교체 연 1~2명
- 향후 **네팔 팀장이 시스템에 직접 입력**할 계획 — 즉 신규 시스템의 주 사용자는 외국인 팀장이다

## 3. 핵심 의사결정: 스프레드시트형 vs 정규화 테이블

### 결론

> **저장은 정규화 테이블. 화면은 스프레드시트 그리드. 종합일보와 HACCP 출력물은 뷰 및 리포트.**

### 3.1 셀 기반(EAV) 저장을 쓰면 안 되는 이유

| 문제 | 결과 |
|---|---|
| D5(행 이동)가 그대로 재현 | 돈방 하나 추가하면 과거 좌표가 어긋남 |
| 제약조건 불가 | "전출 두수 ≤ 재고"를 DB가 검증하지 못함 |
| 집계 쿼리 지옥 | "7월 자돈사 폐사율" 하나에 피벗 로직 필요 |
| 이동 대사 불가 | 발신·수신을 이어붙일 키가 없음 |
| 타입 없음 | `44kg`, `6월 9일`, `/`, `kg` 같은 값이 그대로 들어옴 (현행 실제) |

### 3.2 정규화가 맞는 이유

- 돈방 구조가 안정적이다. 회신 57번 — **신설·폐쇄 없음**. 스키마가 흔들리는 도메인이 아니다
- 두수 이동은 전형적 재고 원장 문제이며 해법이 확립되어 있다
- 이동 1건 = 양방 반영으로 대사 불일치가 구조적으로 소멸한다

### 3.3 화면은 스프레드시트로

- 웹 그리드(AG Grid 등). 열 구성과 순서는 **현행 일보와 동일**하게 유지
- 회신 44번: 돼지 이동 순서(순치사 → 종부사 → 임신사 → 분만사 → 자돈사 → 육성사 → 비육사/검정사)를 따르므로 **현재 순서를 유지**. 단 검정사와 비육사 순서는 교체 요청
- 입력 즉시 하단 검산행 실시간 갱신

### 4.2 돈군(Batch)

입식일·평균생일·전입체중·일령은 돈방이 아니라 **돈군**의 속성이다.

```
batch
  id, farm_id, code
  origin_batch_id     상위 돈군 (계보 추적)
  birth_date_avg      평균생일
  owner_id            부여GP / 중앙축산
  sex_mix             암 | 수 | 암수
  entry_weight_avg
  status              active | closed
```

- 일령 = `보고일 − birth_date_avg`, 주차 = `floor(일령/7)`, 75일령 도달일 = `birth_date_avg + 75`
- 육성사 `#VALUE!`(빈 돈방 일령)는 batch가 없으면 일령을 계산하지 않는 것으로 해소
- 회신 113번 확인: **육성사 위탁판매분은 2회에 나누어 입식**된다 → 한 돈방에 복수 batch가 존재할 수 있으므로 `pen_daily`의 키에 batch_id를 포함한다

### 4.3 이동 원장 — 1:N 구조

회신 64번: **보낸 방은 하나, 받는 방은 여러 곳**으로 분할된다. 8/18 육성사 사례가 그대로 해당한다.

```
movement                      이동 헤더 (발신 단위)
  id, event_date
  from_pen_id                 NULL이면 외부 입식
  from_batch_id
  total_head                  발신 총 두수
  avg_weight_kg
  move_type                   이유전입 | 돈사간전출 | 내부이동 | 되돌림
                              | 출하 | 분양 | 위탁전출
  status                      pending | matched | disputed | cancelled
  reason_code_id, note
  created_by, created_at

movement_line                 수령 분할 (1:N)
  id, movement_id
  to_pen_id                   NULL이면 외부 출하
  to_batch_id
  head_count
  received_by, received_at
```

검증: `SUM(movement_line.head_count) = movement.total_head`. 불일치 시 `disputed`.

**실제 사례 (8/18 육성사)**

| movement | line |
|---|---|
| 육성 1-4방 발신 363두 (40.5kg) | → 비육사 수령 363두 |
| 육성 2-4방 203두 + 2-6방 197두 = 400두 (39kg) | → 검정사 5-1~5-4 수령 400두 |

### 4.4 요일 고정 이동 스케줄

회신 65번에서 확인된 정기 이동이다. 시스템은 이를 **예정 이동**으로 자동 생성하고 실적과 대조한다.

| 요일 | 이동 |
|---|---|
| 일 | 순치사 → 종부사 / 종부사 → 임신사 |
| 월 | 자돈사 → 육성사 |
| 화 | 육성사 → 비육사 및 검정사 |
| 수 | 이유 두수 파악 |
| 목 | 이유 실시 · 분만사(포유모돈) → 순치사 · 분만사(포유자돈) → 자돈사 |

```
movement_schedule
  id, farm_id, weekday, from_house_id, to_house_id, move_type, active
```

- 해당 요일에 예정 이동이 등록되지 않으면 **마감 시 경고**. 이동 자체를 빠뜨리는 오류를 잡는다
- 되돌림 이동(회신 68번): 분만 후 **이유모돈 → 순치사**. `move_type = 되돌림`으로 구분

### 4.6 번식 이벤트 — 관리대장 실물 반영

주차 단위 종이 대장 2종이 번식 데이터의 실제 원천이다. 엑셀 일보의 임신돈 분포도·수태율·유산분석은 모두 이 대장에서 파생된다.

#### 4.6.1 종부 관리대장

**양식 구조** (주 1매, 약 75행, 하단에 (인) 서명란)

```
헤더: 주차 | 교배기간(7/26 ~ 8/1)
행:   번호 │ 모돈: 종부일 · 산차 · 품종 · 교배타임 │ 모돈번호
      │ 웅돈번호: 1회 · 2회 · 3회 │ 분만예정일 │ 임신진단 │ 비고
하단: 총 교배두수 / 재발 / △ / X / 도태 / 총 임신두수 / 수태율
```

**판독으로 확인된 기재 관행**

| 항목 | 실제 기재 | 설계 대응 |
|---|---|---|
| 종부일 | `7/27A`, `7/28P` — **A=오전, P=오후** | `mating_date` + `mating_session(AM/PM)`. **별도 「교배타임」 칸은 전부 비어 있다** — 종부일 접미사로 대체 운영 중이므로 필드를 통합 |
| 산차 | `3`, `1`. 후보돈은 산차 1 + 비고 `후` | `parity`, `is_gilt` |
| 품종 | 대부분 공란 | `breed` (선택 입력) |
| 모돈번호 | 4자리. `1749-A`, `2129-A`, `2617'A'` 등 **-A 접미사** | **이미 등록된 번호를 재사용할 때 붙이는 구분자**(9/8 회신). 따라서 `2129`와 `2129-A`는 **서로 다른 개체**다. 번호는 문자열로 저장하고, 내부 개체 ID(`sow.id`)를 별도로 둔다 |
| 웅돈번호 1회·2회 | 서로 다른 웅돈 (7833/7820, 9808/9557, 8341/7954). 동일 값은 `"` 로 생략 | `mating_line` 1:N — 회차별 웅돈 기록 |
| 웅돈번호에 `Y` | 1회·2회 모두 `Y` | **순종교배(YY) 표시**(9/8 회신). 자체 모돈으로 쓸 후보돈을 생산하는 교배. 웅돈번호가 아니라 **교배유형 플래그**이므로 `mating_type` 필드로 분리 |
| **3회 칸** | 웅돈번호가 아니라 **`재종부 8.17`, `도태 8.21`, `도태예정` 같은 후속 조치**가 적힘 | 후속조치 칸 분리에 **현장 동의 완료.** 다만 **3회 교배도 실제로 발생하므로**(9/8 회신) 3회 웅돈 필드는 존치 |
| 분만예정일 | `11/19`, `12/3` — **종부일 + 114일** | 자동 계산. 손 기입 불필요 |
| 임신진단 | **○ / X / △** (원 표기) | `diagnosis_result: 임신 / 불임 / 의심` |
| △ 후속 처리 | 9/8 회신 | **토요일에 최종 확정** → 미확정 시 **체류돈 자격 획득** → **발정주기 1회전(약 21일) 후에도 발정이 없으면 도태 결정.** 상태 전이를 시스템이 자동 추적 |
| 비고 | `후`, `순치사`, `입수,손`, `다리`, `농`, `7.5 재발`, `6.24 불임`, `유산 7.11`, `8.7 유산`, `7.9 조산` | 코드화 + 자유 텍스트 병행 |
| 정정 흔적 | 33주차 40번 `(1436)X 1740∨` — 모돈번호 취소선 정정 | 시스템에서는 `audit_log` |

**하단 집계 검증 — 종이 계산은 정확하다**

| 주차 | 교배 | 재발 | △ | X | 도태 | 임신 | 수태율 | 검산 |
|---|---:|---:|---:|---:|---:|---:|---:|:--:|
| 31 (7/26~8/1) | 72 | 2 | 1 | 1 | 1 | 67 | 93% | ✓ |
| 32 (8/2~8/8) | 74 | 4 | 1 | 1(불임, 도태예정) | – | 68 | 91.89% | ✓ |
| 33 (8/9~8/15) | 75 | 4 | 1 | – | – | 70 | 93.3% | ✓ |

`임신 = 교배 − (재발 + △ + X + 도태)`, `수태율 = 임신 / 교배`. 세 주차 모두 정확히 맞는다.

**엑셀과의 교차검증 결과 — 완전 일치**

종부사일보 `교배요일` 시트의 주차별 교배 계(31주 72, 32주 74, 33주 75)가 대장 총 교배두수와 정확히 일치한다. `유산분석` 시트의 1710·1768(유산 8/7, 교배일 7/13, 종부사)도 대장 비고란 기재와 일치한다.

**따라서 「거의 매일 발생하는 계산 실수」는 관리대장이 아니라 일보의 두수 합계 쪽 문제다.** 번식 대장은 데이터 품질이 양호하며, 전산화의 가치는 오류 교정보다 **재입력 제거와 자동 파생(분만예정일·수태율·주차 집계)** 에 있다.

**스키마**

```
breeding                        교배 (종부 관리대장 1행 = 1건)
  id, farm_id
  week_no                       주차 (대장 헤더)
  mating_date                   종부일
  mating_session                AM | PM
  sow_ear_tag                   문자열 ('2129-A' 허용)
  parity                        산차
  is_gilt                       후보돈 여부 (비고 '후')
  breed                         품종 (선택)
  expected_farrow_date          = mating_date + 114 (자동)
  mating_type                   일반 | 순종(YY)   ※ 대장의 'Y' 표기
  diagnosis_result              미실시 | 임신(○) | 불임(X) | 의심(△)
  diagnosis_1_date              4주차 1차
  diagnosis_2_date              5주차 2차
  outcome                       임신 | 재발 | 유산 | 불임 | 도태
  location                      종부사 | 임신1동 | 임신2동 | 순치사
  note

mating_line                     교배 회차별 웅돈 (3회까지 실사용)
  breeding_id, seq(1|2|3), boar_ear_tag(nullable — 순종교배 시 미기재)

breeding_action                 후속 조치 (현행 「3회」 칸 오용 해소)
  breeding_id, action_date
  action_type                   재종부 | 도태 | 도태예정 | 기타
  note

abortion                        유산 (유산분석 시트)
  breeding_id, abortion_date
  abortion_age_days             = abortion_date − mating_date (자동)
  location, note
```

주차 집계(교배·재발·△·X·도태·임신·수태율)와 교배 요일별 분포는 전부 `breeding`에서 파생하므로, 하단 집계란과 `교배요일` 시트는 시스템에서 사라진다.

#### 4.6.2 분만 관리대장

**양식 구조** (주 1매, 약 60행, (인) 서명란)

```
헤더: 주차 | 분만기간(8/2 ~ 8/8)

**판독으로 확인된 사항**

| 항목 | 실제 기재 | 설계 대응 |
|---|---|---|
| 동 · 방 | `2동 10방`, `1동 3방` | **`pen_id`로 연결 가능.** 현행 분만사일보 두수표와 개체 대장이 여기서 이어진다 |
| 산차 | 2, 3 | `parity` |
| 품종 | 일부 `YY` 표기, 대부분 공란 | `breed` |
| 총산 분해 | 총산 = 사산 + 미라 + 기형 + 도태 + 체미 + 실산 | **검산 규칙 V6** |
| **사산 칸 복합 표기** | `1+1압사`, `3+2(압사)`, `1(암사)`, `1+1암` | **사산과 압사(생후 압사)를 한 칸에 혼재.** 분만사일보의 도·폐사 현황(압사/아사)과 중복 소지 → 필드 분리 필요 |

| 실산 옆 텍스트 | `유산`, `조산`, `난산`, `난산(암수)` | `farrow_type` 필드 신설 |
| **암 · 수 칸** | **전 주차 공란 — 사용하지 않음** | 존치 여부 확인 필요 (11.2 Q12) |
| **생시체중** | 1.1 ~ 1.7 | **실측값이 아니다(9/8 회신).** 종돈 분양 시 자돈등기대장·혈통증명서에 올리기 위한 형식 기재. **생산성 지표로 쓰면 안 된다** — KPI·이상탐지에서 제외하고, 혈통증명 서류 출력용 필드로만 보관 |
| 주차 번호 | 16(8/2~8/8), 17(8/9~8/15), 19(8/23~8/29), 20(8/30~9/5) | **종부 주차와 분만 주차는 서로 독립된 카운터**(9/8 회신 — "종부사는 종부 기준, 분만사는 분만 기준"). 애초에 대응될 수 없다: 종부 31주차(7/26 교배)의 분만예정일은 11/19이고, 분만 16주차(8/2~8/8)는 4월경 교배건의 분만이다. **주차는 표시용 라벨로만 저장하고, 두 대장은 `breeding.id ↔ farrowing.breeding_id`(모돈 개체 + 교배일)로 연결한다** |

#### 4.6.3 모돈카드 (모돈현황판 / 개체카드)

분만틀·스톨에 걸어 두는 개체별 카드다. 팜스토리도드람B&F 제작 규격 양식을 쓰고 있다. **모돈의 생애 이력이 담긴 유일한 문서**이며, 주차별 대장(종부·분만)을 개체 축으로 뒤집어 놓은 형태다.

**양식 구조**

```

  분만: 분만예정일(+생시체중) · 분만일 · 총산자수
  포유: 전입/전출 · 포유개시
  이유: 이유일 · 이유두수
  특기사항
```

**판독 사례**

| 생년월일 | 2025-04-03 | 2025-02-27 |
| 1산 교배 | 12.29P / 웅돈 1588 | 10.28P / 웅돈 7819 |

| # | 발견 | 대응 |
|---|---|---|
| 1 | **이유두수 12 > 총산 11** (모돈 2589 1산) | 포유 중 **양자(전입/전출)** 로 두수가 바뀐다. 카드에 「전입/전출」 칸이 있는 이유. `piglet_transfer` 이벤트 필요 |

`sow` → `parity_record` → `breeding` / `farrowing` 로 이으면, **모돈카드·종부대장·분만대장 세 문서가 하나의 데이터로 합쳐진다.** 현재는 같은 사실이 세 곳에 따로 적히고 있다.

**개체 마스터 적재 전략 — 사전 일괄 등록을 포기하고 운영 중 축적한다**

모돈 전체 목록(약 1,200두)은 확보되지 않았고, 앞으로도 받기 어렵다. 사전 등록을 전제로 하면 개발이 멈추므로 다음과 같이 우회한다.

| 단계 | 방법 | 확보량 |
|---|---|---|
| 초기 적재 | 확보된 **종부 관리대장 4주치 + 분만 관리대장 4주치**에서 모돈·웅돈 번호를 추출 | 중복 제외 400~500두 (모돈), 웅돈 15두 내외 |
| 운영 중 축적 | 교배·분만 입력 시 등록되지 않은 번호가 나오면 **신규 개체로 자동 생성** | 주당 70~75두씩 추가 |
| 완성 시점 | 종부 사이클 1회전 | 약 4~5개월 후 사실상 전량 |

웅돈은 대장에서 이미 대부분 확인된다 — 4946, 7833, 7820, 9808, 9557, 8341, 7954, 7102, 5147, 2104, 12611, 7819, 2107, 1588 등. 수가 적어 사실상 완결된다.

**미등록 번호가 나왔을 때 오타와 신규를 구분하는 장치**를 둔다. 입력 시 「등록되지 않은 번호입니다. 신규 개체로 등록할까요?」를 묻고, 기존 번호 중 유사한 것(한 자리 차이)이 있으면 함께 제시한다. `2129`를 `2139`로 잘못 친 경우를 이 지점에서 잡는다.

**이 통합이 이 프로젝트에서 가장 큰 중복 제거다.** 모돈 1두의 1산차 정보가 지금은 종부대장 1행 + 분만대장 1행 + 모돈카드 1열 + 일보 두수 반영까지 4곳에 기록된다.

#### 4.6.4 백신 프로그램 (2025년판, 실물 확인)

일령·주령 기준 표준 접종 계획이 확립되어 있다. 시스템은 이를 마스터로 등록하고 **접종 예정일을 자동 산출**한다.

| 대상 | 기준 | 접종 계획 |
|---|---|---|
| **후보돈** | 입식 선발 150~160일령 기준, 일령으로 관리 | 입식 1~2일차 덱토맥스(구충) → 157일 — → 164일 에리셍 파보 → 171일 써코플렉스 → 178일 에리셍 파보 2차 → 185일 콜레라 → 192일 수이셍 → 199일 리니셍 → 206일 구제역 |
| **임신돈(모돈)** | 분만 전 주차 | 6주전 수이셍+DA+로타 → 5주전 구제역 → 4주전 리니셍 → 3주전 수이셍+DA+로타 |
| **포유돈** | 분만 후 주차 | 분만 2주 파보 → 분만 3주 콜레라 |
| **포유자돈** | 주령 | 2주령 히프라 비퓨어(부종병) → 3주령 써코플렉스 |
| **자돈사** | 이유 후 주차 | 6~10주차 회장염 → 7주차 흉막 1차 |
| **육성·비육사** | 생후 주차 | 8주차 콜레라 → 9주차 흉막 2차 → 10주차 구제역 1차 → 14주차 구제역 2차 |

**일괄 접종 (연 단위)**

- 일본뇌염: 4월 3주차, 5월 2주차 — 후보돈·번식돈·웅돈 전체 2회
- 구충: 봄·가을 일괄. 펜벤다졸 또는 이버멕틴 3~4주 사료 첨가

**조건부 항목** — 위축성 비염(초산돈 2회 / 경산돈 1회), 리니셍, 대장균+TGE+로타, 써코플렉스 자돈용은 「필요시」로 표기되어 있다. 마스터에 `is_optional` 플래그를 둔다.

```
vaccine_schedule                표준 접종 계획
  id, target                    후보돈|임신돈|포유돈|포유자돈|자돈|육성|비육
  basis                         일령 | 이유후주차 | 생후주차 | 분만전주차 | 분만후주차 | 연간고정
  offset_value                  157, 8, -6 등
  vaccine_id, is_optional, note
```

이 마스터가 있으면 각 돈군의 `birth_date_avg` 또는 모돈의 분만예정일로부터 **접종 예정일 목록이 자동 생성**되고, 예정일이 지났는데 접종 기록이 없으면 경고(L4)가 뜬다.

### 4.8 사료 재고·투입

급이량은 기록하지 않지만(회신 88번), **돈사별 사료통 투입 기록**이 재고관리 파일에 존재한다. 이것이 사실상 급이량 원장이다.

#### 4.9.3 조달 워크플로우의 전산화

주간 요청 절차가 이미 정형화되어 있으므로 그대로 옮긴다.

```
medicine_request                팀장 주간 요청 (수요일 오전)
  id, request_date, house_id, requested_by
  status                        요청 | 주문완료 | 입고완료

medicine_request_line
  request_id, medicine_id, qty

purchase_order                  본사 취합 주문 (수요일 오후)
  id, order_date, supplier_id
  note                          정기 | 긴급

medicine_receipt                입고 (목요일, 거래명세표 1매 = 1건)
  id, receipt_date, supplier_id, invoice_no
  scan_url                      명세표 사진

medicine_receipt_line
  receipt_id, medicine_id, qty, unit_price(nullable)
```

**현행 요청 리스트 실물은 확보하지 않고 설계를 확정한다.** 카톡·구두 등 비정형으로 주고받는 것으로 파악되므로, 옮겨야 할 기존 서식이 없다. 시스템 화면이 곧 새 표준 서식이 된다.

요청 화면은 최소 구조로 만든다 — **돈사 선택 → 품목 검색 → 수량 입력 → 제출.** 지난주 요청 내역을 기본값으로 불러오면 팀장이 수량만 조정하면 되므로 입력이 1~2분이면 끝난다.

**이 워크플로우가 중요한 이유는 따로 있다.** 팀장이 「어느 파트에서 어떤 약이 얼마나 필요한가」를 매주 스스로 정하고 있다는 뜻이므로, **파트별 약품 소비량은 이미 팀장 머릿속에 있다.** 요청 리스트를 시스템에 넣으면 그 정보가 데이터로 남는다.

#### 4.9.4 여전히 남는 공백 — 투여 기록

조달은 이제 추적된다. 그러나 **어느 돼지에 투여했는가는 여전히 어디에도 없다.**

```
주문 ─────→ 입고 ─────→ [ 공백 ] ─────→ 출하
 ✓ 추적      ✓ 추적      ✗ 기록 없음     휴약 판정 불가
```

거래명세표로 소비 규모를 보면 이 공백이 작지 않다는 것을 알 수 있다.

| 품목 | 8/6 | 8/20 | 8/27 | 9/3 | 8월 합계 |
|---|---:|---:|---:|---:|---:|
| (처)덱소론 50ml (28일) | 50 | 100 | 50 | 100 | **300병** |
| (처)엑스포-피 10g (1일) | 50 | 100 | 50 | 100 | **300개** |
| (처)세프론-주 15g (1일) | – | 25 | 25 | 15 | 65개 |
| (처)안티펜SM 20g (**35일**) | 30 | – | – | 30 | 60개 |
| (처)베트리목신 100ml (21일) | – | 13 | 14 | 18 | 45병 |
| (처)바이트릴100주 50ml (10일) | – | – | 60 | – | 60병 |

**한 달에 항생제만 수백 단위로 소비된다.** 치료 행위가 상시 이루어지고 있으며, 그중 상당수가 10~35일 휴약기간을 가진 품목이다. 기록이 없다는 것은 곧 **출하 시점에 휴약기간 준수를 판정할 근거가 없다**는 뜻이다.

이 공백은 추가 자료로 메울 수 없다. **존재하지 않는 기록이므로, 시스템이 만들어 내는 수밖에 없다.** 4.9.5의 단계적 도입안이 그 답이다.

#### 4.9.5 투여 기록 — 요청 흐름에 얹어 최소 부담으로

투여 기록을 별도 업무로 추가하면 현장이 받아들이기 어렵다. **이미 하고 있는 주간 요청 흐름의 연장선에 두는 것**이 현실적이다.

```
medicine_usage                  투여 기록
  id, event_date, house_id
  pen_id(nullable) / sow_ear_tag(nullable)    돈방 단위 또는 개체 단위
  medicine_id, qty, dose
  operator_id
  withdrawal_until              = event_date + medicine.withdrawal_days (자동)
```

**단계적 도입안**

| 단계 | 입력 단위 | 부담 | 효과 |
|---|---|---|---|
| 1단계 | **돈방 단위** — "자1-3방에 덱소론 2병" | 낮음 | 돈방 전체에 휴약 종료일이 걸림. 과잉 보수적이지만 안전 |
| 2단계 | 개체 단위 — 이각번호 지정 | 중간 | 모돈·후보돈 등 개체 관리 대상에 적용 |

1단계만으로도 **휴약기간 미경과 돈방의 출하 등록을 차단**할 수 있다. 정밀도는 떨어지지만 현행(기록 전무)보다 결정적으로 낫고, 입력은 하루 몇 줄 수준이다.

## 5. 오류 방지·검출 체계

### 5.0 현행에서 오류가 생기고 늦게 발견되는 경로

회신으로 실제 경로가 확인됐다.

| 단계 | 오류 유형 | 현행 빈도 | 시스템 대응 |
|---|---|---|---|
| 작업자 메모 | 관찰 누락, 메모 분실 | 미상 | 요일 스케줄 대비 미등록 경고 |
| 팀장 엑셀 입력 | **계산 실수** | **거의 매일** | 계산 전면 자동화 (P5) |
| 팀장 엑셀 입력 | 수식 깨짐 | 수시 | 수식 개념 자체가 없어짐 |
| 카톡 전송 | **폐사 사진 누락** | 잦음 | 사진 필수 첨부 |
| 카톡 전송 | 캡처 누락·화질 문제 | 가끔 | 전송 단계 소멸 |
| 본사 재입력 | 오독·전기 오류 | 주 2~3회 지적 | 재입력 단계 소멸 |

**계산 실수가 거의 매일 발생한다는 것이 가장 중요한 사실이다.** 검증을 추가하는 것보다 **계산을 사람이 하지 않게 하는 것**이 본질적 해법이다.

**목표 지표**

| 구간 | 현행 | 목표 |
|---|---|---|
| 입력 → 오류 검출 | 익일~수일 | 입력 즉시 (화면에서 차단) |
| 오류 검출 → 원인 특정 | 현장은 장시간 | 클릭 3회 이내 |
| 본사 인지 | 카톡 수신 후 | 입력 확정 즉시 (SSE 푸시) |
| 본사→현장 재확인 | 카톡·전화 | 시스템 내 코멘트 |

### 5.1 5중 방어선

```
L0  필드 검증      입력 즉시(브라우저)   타입·범위·필수         → 셀 빨강
L1  행 검산        입력 즉시(브라우저)   돈방 단위 등식         → 제출 버튼 비활성
L2  트랜잭션 검증  저장 시(서버)         재고·중복·기간         → 저장 거부
L3  돈사간 대사    제출 시(서버)         이동 1:N 짝 맞춤       → 확정 차단
L4  이상 탐지      실시간                통계·스케줄 이탈       → 경고
L5  마감 게이트    일 마감 시            전 돈사 확정 + 예외 0  → 마감 차단
```

### 5.2 L0 — 필드 검증

현행 데이터에서 실제 발견된 오염을 그대로 규칙화한다.

| 규칙 | 현행 사례 |
|---|---|
| 두수는 0 이상 정수 | — |
| 체중은 실수 + 단위 분리 | 육성사 `G` 열에 `kg` 문자열만 들어 있음 |
| 날짜는 날짜 타입만 | 자돈사 입식일 `7-23`, `/` |
| **빈 돈방은 batch 없음으로 표현** | 회신 111번 — 빈 돈방은 셀을 비운다. `/`는 입력 관행 |
| 이각번호 자릿수 | 종부사 1710, 2565 등 |
| 동일 배치 내 입식일 이탈 경고 | 검정사 1-3 `2026-02-25` → 실제 `05-25` (오타 확인) |

### 5.3 L1 — 행 검산 (돈방 단위)

```
당일두수 = 전일두수 + 전입 − (전출 + 내부전출 + 판매 + 폐사 + 도태)
```

- 그리드 각 행 우측에 실시간 검산 뱃지 (✓ / 차이 −1)
- 하나라도 틀리면 제출 버튼 비활성
- **합계·검산은 사람이 계산하지 않는다.** 회신 42번에서 계산란 제거에 문제없음을 확인

분만사는 항목이 많으므로 별도 등식을 둔다.

```
포유자돈 당일 = 전일 + 포유전입 − 포유전출 − 포자사고
분만  : 실산 = 총산 − (사산 + 압사 + 미라 + 기형 + 도태 + 체미)
종부  : 임신두수 = 교배두수 − (재발 + 의심 + 불임 + 도태)
        수태율   = 임신두수 / 교배두수
```

종부·분만 대장의 하단 집계는 현재 손으로 계산하고 있으며 표본 검증 결과 정확하다. 다만 자동 계산으로 바꾸면 주차 마감 시간이 줄고, 무엇보다 **사산 칸 복합 표기(4.6.2) 같은 등식 파괴를 입력 시점에 차단**할 수 있다.

### 5.4 L2 — 서버 트랜잭션 검증

| 코드 | 규칙 | 위반 시 |
|---|---|---|
| V1 | 돈방 검산 등식 | 저장 거부 |
| V2 | `opening(오늘) = closing(어제 확정본)` | 자동 채움, 수정 불가 |
| V3 | 출고 합계 ≤ `opening + in` | 저장 거부 |
| V4 | 동일 (일자, 돈방, batch) 중복 금지 | 저장 거부 |
| V5 | 전일 미확정 상태의 익일 입력 | 저장 거부 |
| V6 | 분만 실산 등식 (압사 분리 후) | 저장 거부 |
| V6-2 | 종부 임신두수·수태율 등식 | 저장 거부 |
| V6-3 | 분만예정일 = 종부일 + 114 (자동) | 입력 불가 필드 |
| V7 | 폐사 두수 = 사유별 합 | 저장 거부 |
| V8 | `SUM(movement_line) = movement.total_head` | 저장 거부 |
| V9 | **휴약기간 미경과 돈군의 출하·도태** | 저장 거부 |
| V10 | 폐사 등록 시 사진 미첨부 | 경고 + 24시간 내 보완 강제 |

V2와 V5의 조합이 전파 차단의 핵심이다. 어제가 확정되지 않으면 오늘이 만들어지지 않으므로 오차가 여러 날을 오염시킬 수 없다.

### 5.5 L3 — 돈사간 1:N 대사

```
[1] 육성사 팀장 입력: "1-4방 발신 363두, 40.5kg → 비육사"
        ↓  movement 생성 (status = pending)
[2] 육성사 재고에서 363두 차감 (홀딩)
[3] 비육사 일보 화면 상단에 "수령 대기: 육성사 1-4방 363두" 배지 상시 노출
[4] 비육사 팀장이 수령 입력 — 도착 돈방을 여러 개로 나눌 수 있음
        ↓  movement_line 여러 건 생성
[5-a] 합계 일치 → matched
[5-b] 불일치 → disputed, 양쪽 화면 + 본사 예외 큐
[6] 마감시각까지 pending 잔존 시 → 일자 마감 차단
```

**입력 횟수: 기존 4회(양쪽 엑셀 2 + 종합일보 2) → 2회(발신 1 + 수령 1).** 수령 입력은 도착 돈방 배분을 위해 어차피 필요한 정보이므로 중복이 아니다.

### 5.6 L4 — 이상 탐지

| 탐지 | 임계 | 등급 |
|---|---|---|
| **일 폐사율 > 1%** | 회신 80번의 정상 범위 기준 | 경고 |
| 폐사 급증 | 돈방 일 폐사 > 평균 + 3σ | 경고 |
| 두수 급변 | 전일 대비 ±20% 변동에 대응 이벤트 없음 | 경고 |
| 실사 불일치 | `reported_closing ≠ closing` | 경고 + 사유 필수 |
| **요일 스케줄 미이행** | 월요일에 자돈→육성 이동 미등록 등 | 경고 |
| 수태율 하락 | **주차 수태율 < 90%** (실측: 31주 93.0 / 32주 91.9 / 33주 93.3) | 경고 |
| **분만예정일 대비 조산** | 실제 분만일 < 예정일 − 5일 | 정보 |
| **재종부 반복** | 동일 모돈 3회 이상 재종부 | 경고 (도태 검토) |
| 사산율 급등 | 사산/총산 > 15% (현행 월계 약 12%) | 경고 |
| 이유 복당두수 이탈 | 평균 11.4 대비 ±30% | 정보 |
| **유산 다발** | 동일 장소·동일 주차 유산 3건 이상 | 경고 |
| 장기 무변동 | 7일 연속 완전 동일 값 | 경고 |
| **사료 재고 대사 이탈** | 시스템 재고 vs 현장 실재고 차 > 3% | 경고 |
| **휴약기간 임박 출하** | 출하 예정 7일 내 휴약기간 종료 | 정보 |

「유산 다발」은 현행 유산분석 시트가 이미 발생장소를 기록하고 있어(임신1동 중앙에 집중) 실제 수요가 확인된 항목이다.

### 5.7 L5 — 마감 게이트

1. 전 돈사 일보 status = confirmed
2. movement 중 pending / disputed 0건
3. 미해소 경고 0건 (사유 입력으로 해소 가능)
4. 실사 불일치 전건 사유 기록
5. 폐사 사진 미첨부 0건

### 5.8 본사 실시간 모니터링

**본사는 종합일보를 취합하지 않는다. 예외만 본다.**

```
┌─ 제출 현황 (18:30 마감) ───────────────────────┐
│ 종부사 ●확정  분만사 ●확정  자돈사 ○작성중      │
│ 육성사 ●제출  검정사 ●제출  비육사 ◐미시작      │
└────────────────────────────────────────────────┘
┌─ 예외 큐 (3건) ────────────────────────────────┐
│ 🔴 비육사 5-1  이동 불일치  발신363/수령361     │
│ 🔴 자돈사 자1-9  폐사 3두 사진 미첨부           │
│ 🟡 육성사 1-4  일 폐사 4두 (재고 대비 1.2%)     │
└────────────────────────────────────────────────┘
```

- SSE/WebSocket 실시간. 카톡 전송·본사 재입력 완전 소멸
- 각 예외는 클릭 시 원천 이벤트 + 입력자 + 시각으로 드릴다운
- 본사 코멘트가 현장 화면에 표시 — 카톡 왕복 제거 (회신 106번에서 대체 가능 확인)

### 5.9 정정 처리

| 상황 | 처리 | 승인 |
|---|---|---|
| 미확정 | 직접 수정, 이력 기록 | 불필요 |
| 확정 후 ~ 마감 전 | 확정 해제 후 수정 | 농장관리자 |
| 마감 후, 당일 한정 | 정정전표 → 당일 보정 | **실장** (회신 105번) |
| 마감 후, 후속일 파급 | 정정전표 → 소급 재계산 | 실장 + 사유 필수 |

월 10건 수준(회신 104번)이므로 정정 프로세스는 가볍게 유지해도 된다. 발행자 ≠ 승인자만 강제한다.

### 6.3 직무분리 (구조 변경)

입력자가 현장 팀장이므로 v1.x의 SoD 전제가 바뀐다. **관찰자와 입력자가 사실상 같은 조직 단위**이므로, 분리는 **현장 대 본사** 축으로 설계한다.

| 규칙 | 내용 |
|---|---|
| SoD-1 | **입력자(팀장) ≠ 확정자(본사).** 팀장은 확정 권한 없음 |
| SoD-2 | 정정전표 발행자 ≠ 승인자(실장) |
| SoD-3 | `admin`은 업무 테이블 접근 불가 (DB 계정 분리) |
| SoD-4 | 마감·마감해제는 `hq_manager` 단독 |
| SoD-5 | **이동 발신과 수령은 서로 다른 팀장이 입력한다.** 현재 담당 구조상 자연히 충족되나, 육성·비육·검정을 한 팀장이 맡으므로 육성→비육/검정 이동은 동일인이 양쪽을 입력한다 |
| SoD-6 | SoD-5의 예외 구간에서는 **수령 입력 시 발신 두수를 화면에 표시하지 않는다.** 저장 후 비교하여 판정 |

SoD-6이 실질적 방어선이다. 발신 363이 보이면 그대로 363을 적게 되므로, 가려야 실제 계수 결과가 입력된다.

### 6.4 입력 환경

| 인터넷 안정 | 오프라인 PWA 불필요. draft 로컬 임시저장만 |

**다국어는 요건에서 제외한다.** 회신 15·16·18·19·21번에서 한국어 항목명을 읽고 이해하며 아라비아 숫자·한국어로 기입하고 현재로 충분하다고 확인됐다. 다만 **오류 메시지는 문장 의존도를 낮춘다** — 이는 언어 문제가 아니라 회신 17번의 "숫자 실수가 많음"에 대한 대응이다.

### 6.5 전자서명과 종이 병행 (HACCP 대응)

**회신 92·93번: 전자기록은 인정되지 않으며 종이를 3년 보관해야 한다.** v1.x에서 검토한 「A안: 시스템이 원본」은 채택할 수 없다.

**확정 방식: B안 — 시스템 입력 → 일보 PDF 출력 → 서명 → 3년 보관**

```
팀장이 시스템 입력 → 본사 확정 → 일보 PDF 자동 생성
                                      ↓
                        현장에서 출력 → 작성자·확인자 서명
                                      ↓
                              돈사별 사무실 3년 보관
```

- 출력물은 **현행 엑셀 일보와 동일한 레이아웃**으로 생성한다. 심사 시 위화감이 없어야 한다
- `daily_report.printed_at`, `signed_at`을 기록해 미출력·미서명 일자를 추적한다
- 시스템 내부에는 `submission_signature`(로그인 세션 + `content_hash`)를 남겨, 출력물과 시스템 데이터가 동일함을 증명한다
- **현행 보관기간이 1년이므로 3년으로 연장해야 한다** (1.5 D12)

이 구조에서 종이는 사라지지 않지만 **손으로 쓰는 종이는 사라진다.** 출력물은 계산이 끝난 결과물이므로 계산 오류가 원천적으로 없다.

### 6.6 감사로그

전수 기록: 로그인·로그아웃·실패, 권한 변경, 모든 업무 데이터 변경(전·후 값), 확정·해제·마감, 정정전표, 데이터 내보내기.
append-only. 애플리케이션 DB 계정에 UPDATE/DELETE 권한 미부여. 보존 3년(HACCP 기준과 동일).

## 7. 시스템 아키텍처

### 7.1 구성

```
[현장사무실 PC 3대]  Chrome / 팀장 4계정

**돈사별 전용 탭**

- 종부사: 임신돈 분포도(주령 1~17), 교배·사고·수태율, 유산 등록
- 분만사: 분만 현황(총산·사산·흑자·미라·기형·체미·실산), 도·폐사 현황, 이유 현황

- 검정사: 일령, 종돈 분양·판매, 비육도태, 이각번호

**키보드 조작**

| 키 | 동작 |
|---|---|
| Tab / → | 다음 셀 |
| Enter / ↓ | 다음 행 |
| 숫자패드 | 즉시 입력 |
| `0` | 변동 없음 확정 |
| Ctrl+S | 임시저장 |

**빈칸과 0의 구분.** 현행은 변동 없는 돈방을 빈칸으로 둔다(회신 33번). 시스템에서는 전 돈방 필수 입력으로 두고 변동 없으면 명시적 `0`을 찍게 한다. 미입력 행이 있으면 제출이 막힌다.

**금지 기능:** "전날 값 전체 복사" 버튼은 만들지 않는다. 회신 48번에서 현재 전일두수를 복사해 쓰고 있으나, 시스템에서는 자동 이월이므로 복사가 필요 없다.

## 10. 개발 로드맵

오류 검증·권한·PDF 출력은 후반부 기능이 아니라 1단계 골격이다.

| 단계 | 범위 | 기간 |
|---|---|---|
| 1 | 마스터 + 인증·권한 + 돈사 1곳(자돈사) 일보 입력 + L0~L2 검증 | 5주 |
| 2 | 전 돈사 6종 확대 + L3 1:N 이동 대사 + 마감 + 본사 예외 큐(실시간) | 6주 |
| 3 | 종합일보 뷰 + 확정·정정전표 + 감사로그 + **일보 PDF 출력(HACCP)** | 4주 |
| 4 | 번식 이벤트(교배·임신진단·분만·이유·유산) + **모돈 개체 관리(모돈카드 대체)** + 폐사·도태일지 + L4 이상탐지 | 6주 |
| 5 | 사료·약품 재고 + **약품 사용 기록 신규 구축 + 휴약기간 자동 검증** + 백신 예정일 알림 + 출하·정산(경락가 연동) | 5주 |
| 6 | KPI 대시보드 + HACCP 신고 + 한돈팜스 입력 보조 화면 | 3주 |

병행운영 4주 포함 시 약 7.5개월.

**1단계 완료 시점에 이미 얻는 것:** 자돈사 한 곳에서 전일두수 자동 이월, 돈방 단위 검산, 계산 자동화, 입력자·시각 기록. 「거의 매일 발생하는 계산 실수」가 이 시점에 사라지므로, 나머지 확대의 근거를 바로 확보할 수 있다.

**우선순위 재검토:** 5단계의 **휴약기간 자동 검증**은 안전·규제 측면에서 가치가 높다. 현재 사람의 기억과 종이 모돈카드에 의존하고 있으므로, 여건이 되면 3단계와 순서를 바꾸는 것을 권한다.

| 모돈번호 `-A` | **기등록 번호 재사용 시 구분자.** `2129`와 `2129-A`는 다른 개체 |
| 웅돈번호 `Y` | **순종교배(YY).** 자체 모돈용 후보돈 생산 교배 |
| 임신진단 △ 처리 | **토요일 최종 확정 → 미확정 시 체류돈 전환 → 발정주기 1회전 후 무발정 시 도태** |
| 3회 교배 | **실제로 발생함.** 필드 존치 |
| 생시체중 | **실측 아님.** 혈통증명서용 형식 기재 |
| 압사 칸 분리 | **현장 동의 완료** |
| 후속조치 칸 신설 | **현장 동의 완료** |
| 한돈팜스 | 파일 업로드 불가, 사이트 직접 입력 |
| 약품 투여 기록일지 | **존재하지 않음** (조달 기록은 존재) |
| 약품 조달 주기 | **매주 수요일 오전 팀장 요청 → 오후 주문 → 목요일 납품.** 거래명세표 6매 일자가 전부 목요일로 일치 |
| 약품 공급처 | AG동물약품(일반), 축협(구제역 전용) |
| 휴약기간 정보 | 거래명세표에 품목별 인쇄. **최장 35일**(안티펜SM), 33일(툴라신), 28일(덱소론·덱사메타손·복합부스코판) |
| 월간 항생제 소비 | 덱소론 300병, 엑스포-피 300개 등 — **치료 행위가 상시 발생** |
| 백신 프로그램 | 2025년판 확보. 일령·주차 기준 확정 |
| 조직도 | 26.07.20판 확보. 현장 18명 + 본사 4명 |
| 종부·분만 주차 체계 | **서로 독립된 카운터.** 대응 불가하며 개체+날짜로 연결 |
